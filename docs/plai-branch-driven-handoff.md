## Branch-driven workflow friction seen in the hackathon

1. A teammate removed the public safety gate from `main` without reconciling the separate safe drawer branch; PR #42 then merged despite a formal Changes Requested review. Review state was not a protected effect. Keep the user's explicit decision to freeze `main` as a branch-scoped policy receipt.
2. GitHub CI and Vercel differed: a successful PR Preview and green CI did not prove the merged staging alias served that SHA. The Neon integration can fail **before** build. Model code SHA, PR target, GitHub checks, deployment ID/status, alias and browser response as separate witnesses.
3. Staging pushes initially had no CI trigger; PR #44 added it. A successful feature-branch test is not merged-commit evidence.
4. A handoff researcher initially inferred the Firepoint remote from unrelated TriggerPoint cwd and wrote wrong repository links; parent corrected them to `Astrotemporal/firepoint`. Bind every task and handoff to verified cwd + remote + base/head SHA. A completed UI child was once shown as “running” in the roster until observed and explicitly deleted: distinguish stale activity from pending work.
5. Neon branch provisioning and rights/privacy gates are independent. Do not solve a branch quota by blindly deleting databases, upgrading a plan, enabling PR #34, or pretending an old Preview is current.
