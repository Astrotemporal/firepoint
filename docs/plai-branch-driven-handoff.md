## Branch-driven workflow friction seen in the hackathon

1. A teammate removed the public safety gate from `main`, and PR #42 merged despite Changes Requested. Review state was not a protected effect. Keep the owner's explicit gate-free prototype decision scoped to `main`; do not copy it to staging or turn it into a safety endorsement.
2. A successful feature PR check or staging push CI does not establish an alias-bound deployment. The Neon branch quota once prevented Vercel builds before app compilation. The original Git-backed staging Preview is verified at `792aad2`, while the separate no-Neon manual site remains at `44c1f29` before its next redeploy. The latter observation does not bind current staging code. Model repo/ref/PR base, CI SHA, Vercel project/target/deployment SHA, alias and anonymous browser response as distinct witnesses.
3. Staging pushes initially lacked CI until PR #44. GitHub Actions screenshots remain read-only artifacts; checked-in README images require a manually reviewed PR and can lag either branch.
4. A prior handoff inferred a wrong Firepoint remote from a TriggerPoint cwd. Bind each task to a verified remote and isolated checkout. Distinguish an old completed worker from pending work rather than trusting stale roster activity.
5. Neon branches, deployment protection, report privacy and agency source rights are independent gates. Do not blindly delete databases, upgrade a plan, enable reports or promote a staging alias to solve another gate.
