# Planning model seam, not evacuation zones

**Status:** Firepoint has **no WindNinja or ELMFIRE run, time-of-arrival raster, measured clearance time, fire forecast, trigger line or source-backed prediction map**. `src/planning/scenario.ts` is a pure, unconnected validation/comparison contract with synthetic-only tests. It never calls a model, fetches an API, persists a run, draws geometry or issues an instruction. PR #53 merged source-cache schema hardening on staging, but migration `0101` is not applied to Neon and no runtime source-cache feed or planning model was added. Do not feed synthetic test values to the resident UI.

## What the current map actually draws

On `staging/source-backed`, the homepage has no default simulated Verdugo fire (PR #16). Merged PR #19 made private device marks **grey dashed, display-only 500 m sketches**; they do not steer routes or change status. Dormant PR #45 yellow report-activity badges receive `null` on the public map, so no yellow circle is drawn without validated activity. The staging production-mode release gate hides the developer routing prototype. Separately, the public `main` Production prototype is intentionally gate-free and must not be mistaken for the gated staging map. Neither branch has an agency fire perimeter, evacuation order, spread forecast or verified route; hardcoded shelter/escape targets in prototype code are not agency destinations. See the [source policy](source-policy.md) for the release boundary. NWS/CAL FIRE/NIFC/AirNow/Glendale GIS source contracts are not connected to private sketches; production source queries remain paused.

**Red = order / yellow = warning only when the issuing agency publishes that status and its applicable zone or polygon.** The app cannot derive an official order/warning from a distance to a fire, three marks, report density, a wind field or a model contour. Agency shapes need original issuer wording/URL, ID, issue/retraction time, verified jurisdiction and geometry vintage. NIFC perimeters mean mapped fire extent **at capture time**, not today's front or an order. Community report-density cells stay visually and contractually unverified.

## A separate conditional planning computation

A future batch pipeline could run the [USFS WindNinja CLI](https://github.com/firelab/windninja) on sourced terrain and HRRR initialization to produce **terrain-adjusted wind**, then a **separate, validated** spread model such as ELMFIRE on cited ignition, fuels/terrain and wind to produce time-of-arrival (TOA) cells. Clearance time would need separately verified households/vehicles/exits/mobilization and a safety margin. None is available in Firepoint today. A WindNinja grid alone says nothing about where fire will travel.

The new `PlanningCellSchema` requires WindNinja and ELMFIRE run/version/configuration/output hashes, a matched wind-run ID, sensible run/input retrieval times and simulation horizon, cited DEM/wind/fuels/ignition and household/vehicle/exit sources, a clearance method, and an explicit **detection/alert delay** with its own source. TOA starts at modeled ignition; clearance starts only after the notification delay, so the comparison is **TOA − alert delay − clearance − safety margin**. Mobilization belongs in the cited clearance method; it must not be silently omitted or double-counted.

Each wind/fire/clearance review is structured with its URL, time, acceptance outcome and the exact configuration hash it assessed. `evaluatePlanningCell` returns `unavailable` for absent TOA, a run older than the caller's explicit `maxRunAgeMin` at `evaluatedAt`, missing/pending/rejected or mismatched reviews. Unavailable outputs **hide the arrival value and slack**. A URL or accepted flag by itself cannot prove a report is genuine: an independent reviewer still must check report contents and source rights. The age policy does not make a run live/current, prove its inputs have not been superseded, or establish a wind-field validity window beyond its recorded initialization. There is no automatic standing-zone or event authority here.

Its three successful outputs are **model-only** time comparisons (`modeled-clearance-deficit`, `modeled-within-safety-margin`, `modeled-margin-met-under-assumptions`), **never** “evacuate,” “warning,” a safe area or an all-clear. Every output carries the input provenance, review records, time assumptions and fixed caveats: lee-canyon underprediction, dated fuels, spotting and notification/mobilization limits. This is a *planning projection, not a forecast or evacuation order*.

TOA is a raster surface, not a ring: terrain, wind, fuels and spotting break radial symmetry. If the team later validates a projection layer, map cells/contours must come from the real model output and have an explicit hypothetical-scenario mode with vintage, validation and uncertainty. Do not draw a synthetic red/yellow radius from the formula. A planning deficit may prompt **planner review**, not an automatic resident evacuation instruction. Official alert channels remain the resident action source.

## What still has to be built

1. Select and license the model inputs; run a pinned WindNinja container/CLI and a separate spread model; record full provenance sidecars and immutable output hashes. No publicly documented, licensed WindNinja API is available to Firepoint; plan for a reproducible batch run instead.
2. Validate against historical Santa Ana winds and observed fire perimeters/arrival, including lee-slope error and spotting limits; commission clearance input verification. The contract's validation URLs must refer to real reports, not test fixtures.
3. Design an atomic worker/store/export path for **complete** run generations and source checks (proposed separately in [PR #15](https://github.com/Astrotemporal/firepoint/pull/15); not merged or connected). Never replace last-good with partial output or call an old run current.
4. Have the map/API/frontend owners review distinct symbology and error states, then test real cell-to-map georeferencing, scenario change, stale/absent run and official-geometry separation. No model layer should render in the resident default view before source/agency and release review.

The tests in `src/planning/scenario.test.ts` use conspicuously synthetic values **only inside tests**. They cover time comparisons and delay boundaries, missing/stale/rejected/mismatched reviews, cross-run and source-time mismatch, simulation horizon, invalid units and no order/color/polygon/all-clear fields. Passing those tests says the contract is safe to extend; it does **not** validate a physical wildfire model.
